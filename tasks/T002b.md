## Task
Close the NAT leg of the T2 QUIC movement spike: verify a client can connect
to `spike-quic`'s server through a real home router's NAT, with no manual
port forwarding.

## Crate(s)
None in this workspace. Uses the existing throwaway repo
`C:\CRPG\Dev\spike-quic` (unchanged, unless the connection fails for a
reason within the spike's own control — see Out of scope). This file exists
to make the result traceable from the main repo, per `docs/HANDOFF.md`'s
task-numbering convention.

## Purpose
ADR-0004 marked T2 a "conditional go": the prediction/reconciliation design
is validated, but the NAT half of the spike's own test criteria
(`CRPG_ENGINE_SPEC.md` §24: "a connection succeeds over the public internet
through NAT") was never run — the session that built the spike had only one
machine. Spec §7.7 explicitly defers NAT punching/relay as a *feature*, but
that's a decision about handling failure gracefully; whether the base case
(server behind an unmodified home router just... works) succeeds or fails
was never actually observed. This is the only item keeping T2 from being
closed.

## Requires — human, not agent
This cannot be executed by a coding agent in a single-machine sandboxed
session. It needs a person with two machines on different networks — e.g.
this dev box behind its home router as the server, and a phone hotspot,
another location, or a cheap cloud VM as the client's network (or the
reverse: server on a VPS, client here).

## Behaviour
1. Run `server.exe` from `spike-quic` on one machine, behind its normal
   router/firewall, with **no manual port forward and no DMZ**.
2. From a second machine on a genuinely different network, run
   `client.exe <public-ip-or-ddns>:5000`.
3. Observe whether the QUIC handshake completes and movement
   intents/acks flow (same reconciliation behaviour as the local runs in
   ADR-0004).
4. Record the outcome exactly as observed — success, outright failure, or
   partial (e.g. handshake completes but datagrams never arrive) — plus any
   router-specific detail that would explain it (UPnP/NAT-PMP on or off,
   suspected CGNAT/ISP-grade NAT, symmetric vs. cone NAT if determinable).

## Test
A connection either succeeds with zero manual configuration, or the failure
mode is captured precisely enough to know whether it is fixable now (e.g.
enable UPnP) or falls under spec §7.7's already-deferred scope (NAT
punching / relay / login server) and is expected to fail without that
future work.

## Definition of done
- `docs/adr/0004-quic-movement-spike.md` updated: the "NAT leg: not

- `docs/PROJECT_STATE.md` updated to reflect the outcome (T002 fully closed,

## Out of scope
No code changes to `spike-quic` unless the failure is due to something
trivially within the spike's own control (e.g. binding to the wrong
interface/address). A failure caused by the network itself (symmetric NAT,
CGNAT) is a finding to record, not a bug to fix here — that's future NAT
traversal / relay work, already out of scope per §7.7. Do not touch
`crates/`, `tools/lint/`, or `.github/workflows/ci.yml`.
