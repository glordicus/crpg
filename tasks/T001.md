## Task
Run the GDExtension rendering spike and record a go/no-go decision.

## Crate(s)
None in this workspace. The work happens in the separate throwaway repo
`C:\CRPG\Dev\spike-gdext`, which has no dependency on the `crpg` workspace.
This file exists only to make the decision and its rationale traceable from
the main repo, per `docs/HANDOFF.md`'s task-numbering convention.

## Purpose
Spec `CRPG_ENGINE_SPEC.md` §1.4/§24 (T1) identifies the load-bearing
assumption of the whole architecture: that Godot can render CRPG-scale
content driven entirely by external Rust state across the GDExtension FFI
boundary, fast enough to be usable. Nothing past this point in the roadmap
should be trusted until this is measured.

## Interface
N/A — not a library API. The spike repo exposes one GDExtension class
(`CharacterHerd` or similar) to a Godot scene; no interface is consumed by
this workspace.

## Behaviour
In `C:\CRPG\Dev\spike-gdext` (already has a working `godot`-crate toolchain
proof, `HelloProbe`, committed as a baseline first):
- A Rust-side array of up to 1,000 `{position, rotation, anim_state}`
  structs, updated at a fixed 20 Hz.
- Godot spawns that many skinned `Node3D` proxies, interpolates between the
  20 Hz updates, and drives `AnimationTree` from `anim_state`. No gameplay
  logic in GDScript.
- Measure frame time at 200, 500, and 1,000 characters on the RTX 4060
  laptop, and measure per-tick FFI cost separately from render cost.

## Test
Run the Godot project at each population size and read the on-screen
fps/FFI counters. There is no `cargo test` gate — this is a spike.

## Definition of done
- 200 characters at ≥ 60 fps with FFI cost under 1 ms per tick: **go**.
  Otherwise: **no-go**, escalate to a Bevy spike per spec §1.4.
- Either outcome is written up as `docs/adr/0003-gdextension-rendering-spike.md`
  in this repo, with the actual measured numbers.
- `docs/PROJECT_STATE.md` updated with a one-line pointer to the ADR.
