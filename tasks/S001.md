## Task
Harden the public-repo attack surface opened by the security review: a
fork-PR guard for `tools/lint/` and `.github/workflows/`, a `build.rs` ban, a
secret scan, a self-hosted-runner rule, and a `deny.toml` tightening.

## Crate(s)
None. Touches `tools/lint/deps.py`, `tools/lint/test_deps.py`,
`.github/workflows/ci.yml`, `deny.toml`, `docs/AGENTIC_WORKFLOW_PLAN.md`,
`docs/PROJECT_STATE.md`, `tasks/BACKLOG.md`. No crate is opened, so no
architecture doc is due (BACKLOG "readiness gate" rule).

## Purpose
The repo is public, so its code arrives untrusted twice: fork PRs execute on
GitHub-hosted runners, and whatever gets merged executes on the maintainer's
machine at the next local `cargo build`/`cargo test` — with credentials
(rustup, crates.io, OpenCode provider keys) in reach. The security review
found four concrete gaps, all cheap to close now and expensive later:

1. **Defangable lints.** `tools/lint/deps.py`, `tools/lint/determinism.py`
   and their self-tests live in the same tree the lints police. A PR (or a
   compromised agent) can rewrite a lint *and* its selftest in one commit and
   CI stays green — which would admit an out-of-graph dependency edge, an
   extra `unsafe` block, or a `build.rs` that runs code at build time.
2. **No build.rs ban.** Nothing forbids a crate root `build.rs` or an
   external `[build-dependencies]` entry. That is arbitrary code executed on
   the maintainer's machine at every local build. `deps.py` currently checks
   workspace edges only.
3. **No secret scan.** Content PRs and agent-written files will eventually
   carry credentials; a committed key on a public repo is a leak with no CI
   tripwire.
4. **Self-hosted-runner RCE.** Workflow plan §7 Stage 4 / §15 item 16 plans a
   self-hosted runner on the desktop. The prose already says "restricted to
   your own branches" but nothing enforces it; any `pull_request`-triggered
   job reaching a self-hosted label is arbitrary code on the LAN. The rule
   has to be structural before a runner exists.

The guard's honest limits are stated under Behaviour: a workflow cannot
defend itself against a fork PR that deletes the jobs it contains, so branch
protection (a human, repo-settings item) is the real boundary — this task
makes the automated layers tripwires and records the settings change as a
required human step in Definition of done.

## Interface
- `python tools/lint/deps.py` exits 0 on the current tree, with the new
  build.rs checks.
- `python -m unittest discover -s tools/lint -p "test_*.py"` passes.
- The `guard` job exists in `ci.yml` and is green on a clean PR.
- `cargo deny check` is clean with `yanked = "deny"`.

## Behaviour

**1. deps.py — build-script ban.**
Add `check_build_scripts()`:
- Any `build.rs` at a crate root (next to its `Cargo.toml`) is a violation,
  for every crate: `VIOLATION <name> (build.rs at crate root)`.
- Any non-workspace entry in a `[build-dependencies]` table — top-level or
  under `[target.*]` — is a violation:
  `VIOLATION <name> -> <dep> (external build-dependency, <label>)`.
  Workspace `[build-dependencies]` are already caught by the layering check.
- No allowlist today. An entry later is an ADR decision, the same class as a
  `deny.toml` widening (T005c precedent).

Extend the module docstring, which currently names four checks, to name
five. In the new check's doc comment, say *why*: a build script runs code on
every consumer's machine at compile time, so admitting one is admitting
arbitrary local execution, not just an import.
Do not touch `tools/lint/determinism.py` or its selftests.

**2. ci.yml — `guard` job (fork-PR tripwire + trusted-lint gate).**
New job `guard`, `runs-on: ubuntu-latest`, near the top. Two sub-checks,
implemented with plain `git`/`bash` or the existing Python invocations —
no new third-party action:

a. **Protected paths.** If `github.event.pull_request.head.repo.full_name`
   is a fork (`!= github.repository`) AND `git diff --name-only` over the
   merge-base touches `tools/lint/**` or `.github/workflows/**`, fail with a
   message naming the policy. Same-repo PRs are exempt from *this* sub-check
   only (only the maintainer pushes branches to the repo). The check must
   gate on the fork repo URL alone — a fork PR has no write access to
   repository variables or secrets, so the fork cannot flip any switch.

b. **Trusted-lint gate (every PR, same-repo included).** Restore
   `tools/lint/` to the merge-base copy (`git checkout <merge-base> --
   tools/lint`), then run the existing three invocations — `deps.py`,
   `determinism.py`, and the unit selftests — against the PR tree. A PR that
   weakens a lint *and* its selftest together is still judged by the trusted
   definitions and fails. This is the tripwire for agent PRs as well as for
   forks.

**There is no automation bypass for sub-check b.** The "override" for a
legitimate lint change is the ordinary repo process: the maintainer reviews
and merges it as a deliberate commit (the same discipline as a `deny.toml`
widening). No secret, variable, or comment convention may disable the gate —
fail closed is the point.

A one-line comment at the workflow's `on:` block records the policy the job
enforces: *fork PRs run on GitHub-hosted runners only; CI and lint changes
from fork PRs are rejected by the guard job; the self-hosted runner never
receives a pull_request-triggered job.*

**3. ci.yml — `secrets` job.**
A `gitleaks` scan of the tree on every push and PR. Either
`gitleaks/gitleaks-action` pinned to an exact version, or install the
`gitleaks` binary directly — mirror the `deny` job's pin-by-exact-version
rule. Default rules, no allowlist. If the first full scan finds anything in
history, stop and report it — do not rewrite the finding to make CI green.

**4. deny.toml.**
Change `yanked = "warn"` to `yanked = "deny"` and update the header comment:
a yanked crate is often yanked *because* it is compromised; tolerating one
at "warn" quietly admits a crate that was pulled for cause.

**5. Self-hosted-runner rule in the docs.**
Rewrite the workflow plan's runner text (§7 concrete-setup note and §15 item
16) from "restricted to your own branches" (prose) to a stated, enforced
rule: the runner executes only `push` on the base repo's own branches, or
`workflow_dispatch`; a `pull_request`-triggered job using a custom
`runs-on:` label is a CI failure — enforced by the guard job's
protected-paths rule over `.github/workflows/**` — not a configuration
accident.

**6. BACKLOG — deferred crate-contract notes.**
Append to "Not yet numbered" the three input-hardening requirements so they
land with the tasks that own them:
- `T010` `crpg-data` loader caps: campaign JSON file size and nesting-depth
  ceilings (`serde_json` recursion is a stack-overflow DoS).
- `T018` `crpg-net` postcard decode caps: message size, and `Vec`/`String`
  length ceilings (a hostile length field is an OOM).
- `SnapshotBackend` (`crpg-persist`): decompression-bomb cap on `zstd`
  saves — input size *and* decompressed-size ceiling.

Also update `docs/PROJECT_STATE.md`: "Known problems" notes the gaps this
task closes, and any entries it fixes are removed or pointed at this task in
the same commit.

## Constraints
- No Rust file, no crate `Cargo.toml`, no new workspace dependency, no new
  crate. `rust-toolchain.toml` and `crpg-contracts` untouched.
- Do not touch `tools/lint/determinism.py` or its selftests, and do not
  weaken any existing lint, test, or CI step to make the new checks pass.
- The guard uses `git`/`bash` and the existing Python invocations only. The
  only new CI tool is gitleaks — a CI tool, not a crate dependency
  (T005c's `cargo deny` precedent).
- Sub-check a must not be satisfiable by a value the fork PR controls; gate
  on the fork repo URL only.
- If a change to the working tree makes `deps.py` fail for a reason unrelated
  to this task, stop and report rather than adjusting the check.

## Test
- `cargo deny check` exits 0 (`yanked = "deny"` clean on the current tree).
- `tools/lint/test_deps.py` grows cases: a crate with a root `build.rs`
  fails; a crate with an external `[build-dependencies]` entry fails
  (top-level and `[target.*]` variants); no workspace crate falsely trips
  the ban; existing cases still pass.
- Deliberate break commits, reverted before finishing (T005c pattern):
  - a temporary `build.rs` in one crate makes `deps.py` fail naming it;
  - a temporary dummy secret makes the `secrets` job fail;
  - a branch editing a lint *and* its selftest fails the guard job's
    trusted-lint step even with the selftest rewritten.
- Simulate the fork-PR path check locally (a scratch branch editing
  `tools/lint/` diffed against master) and confirm sub-check a trips.

## Definition of done
- [ ] Every gate the root `AGENTS.md` lists runs clean, plus
      `cargo deny check`.
- [ ] `guard` and `secrets` jobs in `ci.yml`; both green on a clean PR, with
      no new third-party action beyond gitleaks.
- [ ] `deps.py` build.rs/build-dependency ban implemented, documented, and
      selftested; a temporary `build.rs` demonstrably fails it.
- [ ] `deny.toml` `yanked = "deny"`.
- [ ] `docs/AGENTIC_WORKFLOW_PLAN.md` runner section states the enforced
      rule; `docs/PROJECT_STATE.md` and `tasks/BACKLOG.md` updated,
      including the three deferred crate-contract notes.
- [ ] **human** — branch protection enabled in repo settings: required
      status checks on PRs, and PRs that modify `tools/lint/**` or
      `.github/workflows/**` require explicit maintainer review. This is the
      boundary the guard jobs themselves cannot enforce, and the task is not
      done without it.

## Out of scope
- Building anything in `crpg-data`, `crpg-net`, `crpg-persist`, `crpg-script`;
  their hardening is recorded as deferred notes only.
- Actual self-hosted-runner setup, the merge queue, dependabot, `cargo
  audit` as a platform, secret rotation.
- GitHub *settings* beyond the single control named in Definition of done
  (branch protection); other review recommendations (CODEOWNERS, Dependabot)
  stay out of this task.
